# QA Android — operasi inventori dan profil POS (31 Oktober 2026)

> Putaran lanjutan 1 November (Retail + Simple, API PO + UI Android penerimaan sisa, uji jumlah berlebih, serta perbaikan metadata retry/skeleton) dicatat terpisah di [QA_E2E_LANJUTAN_20261101.md](QA_E2E_LANJUTAN_20261101.md). Hasil terbatas tersebut tidak menggantikan matriks profil yang belum diuji di bawah.

## Ruang lingkup dan batas pembuktian

Pengujian memakai APK **staging** Pantoo POS di emulator Android 16, API lokal port 8082/8083 (8083 untuk memuat perbaikan server), dan MongoDB replika **sementara di loopback**. Data QA tidak menyentuh instansi produksi. Akun, toko, lokasi toko/pusat/transit, satu barang stok, satu layanan nonstok, dan supplier dibuat khusus QA. Hasil di bawah membedakan operasi yang benar-benar selesai dari menu/form yang hanya berhasil dibuka.

Profil POS yang tersedia: retail, restoran, laundry, bengkel, salon, jasa, custom. Profil inventori: simple, centralized, advanced. [Laporan pengujian sebelumnya](QA_ANDROID_PROFIL_POS_INVENTORI_20261030.md) memeriksa pemuatan tujuh profil POS serta tiga profil inventori untuk jalur dasar. **Laporan ini tidak menganggap pemeriksaan sebelumnya sebagai bukti E2E untuk setiap kombinasi 7 × 3.**

## Temuan dan perubahan

1. **Retur Android sebelumnya ditolak server.** Query ketersediaan dan payload retur belum menyertakan ID penerimaan/tagihan dan identitas stok yang wajib cocok dengan sumber. Diperbaiki di `lib/data/graphql/purchase_return_queries.dart` dan `lib/presentation/pages/pos/pos_purchase_return_page.dart`; pembuatan serta pengiriman retur kemudian berhasil di emulator.
2. **Detail retur gagal karena kontrak GraphQL.** `getOnePurchaseReturn()` mem-populate `purchase_id` menjadi objek, sementara field schema bertipe `ID`. `graphql/purchase_return/purchase_return.service.js` kini mengembalikan `purchase_id` sebagai ID dan objek lengkap pada field `purchase`. Diverifikasi melalui server QA kedua dengan kode baru: detail terbaca di Android, approval dan proses lewat API berhasil, jurnal `posted`, serta stok turun tepat satu. UI tombol approval/proses Android masih perlu skenario retur baru.
3. **Pemilih barang mutasi stok sempat menghambat.** Pada APK awal, tombol Scan/Tambah nonaktif setelah sumber diganti ke Lokasi Toko QA, walau API mengembalikan 51 unit. Kode pemuatan barang kini menolak respons usang ketika pengguna mengganti lokasi sebelum permintaan sebelumnya selesai (`pos_inventory_editor_page.dart`). Pada APK baru, pemilih dan kelanjutan mutasi berhasil diuji sampai penerimaan.
4. **Detail mutasi Android crash pada jumlah bulat.** `received_qty` dari API bernilai bilangan bulat, tetapi `_compactNumber` hanya menerima `double`, sehingga detail draft menjadi layar merah. Formatter di `pos_inventory_page.dart` kini menormalkan `num`/teks/null; APK dibangun ulang dan seluruh tahap mutasi selesai di emulator.
5. **Ajukan mutasi gagal di server.** Resolver `SubmitInventoryTransfer` mengakses variabel `input` yang tidak ada pada argumen mutation `{id}`. Validasi biaya dipindahkan ke dokumen mutasi yang ditemukan. Setelah server QA diperbarui, ajukan dari Android berhasil.
6. **Transaksi bayar langsung tidak masuk dapur.** Jalur `ProcessPOSPenjualan` membuat order operasional tanpa menyalin mode persiapan/stasiun dari produk. Akibatnya item memakai default `instant/not_required`, walau produk `station`. Resolver kini membangun snapshot persiapan dan stasiun untuk order yang dibuat saat checkout langsung. Reproduksi dan uji ulang di Android membuktikan tiket baru muncul dan status dapat berpindah sampai Siap.
7. **Fixture awal tidak punya COA persediaan**, sehingga penerimaan mula-mula ditolak `Akun persediaan 1100 harus aktif, detail, dan bertipe aset`. Setelah akun QA ditambahkan, penerimaan berhasil. Ini bukan bukti bahwa onboarding instansi baru otomatis menyiapkan COA tersebut; perlu uji onboarding tersendiri.
8. **Fixture awal juga tidak punya lokasi transit baku**, sehingga proses mutasi menolak dokumen yang sudah disetujui. Setelah lokasi transit QA dengan tipe `in_transit` ditambahkan ke profil, alur berhasil. Onboarding profil centralized tetap perlu pembuktian tersendiri.
9. Pada konfirmasi ajukan PO, label “Cabang: -” muncul walau tujuan `Lokasi Toko QA` terpilih. Ini ketidaktepatan informasi UI, bukan kegagalan simpan PO.
10. Pemilih barang PO menampilkan `Layanan QA Android` yang tidak melacak stok. Perlu putuskan apakah layanan memang boleh dibeli sebagai biaya; jangan menerimanya sebagai penerimaan stok tanpa aturan yang jelas.
11. **Order lama yang lahir sebelum perbaikan dapur tidak otomatis berubah.** `ORD-20261031-0001` pada fixture QA tetap `Baru` dengan item `instant/not_required` meski produknya kini bertipe `station`. Ini membuktikan perbaikan jalur checkout hanya berlaku untuk order baru. Sebelum menganggap data produksi bebas antrean tersangkut, audit order lama berdasarkan snapshot transaksi dan putuskan rekonsiliasi manual yang aman; jangan mengubah riwayat order secara massal tanpa persetujuan.
12. **Simpan ke Meja gagal bila shift tidak wajib.** `CreatePOSOrder` melakukan query `_id: ""` pada model shift sebelum memeriksa kebijakan `allowOutOfShift`, sehingga Mongoose melempar `Cast to ObjectId failed`. Resolver kini hanya mencari shift jika ID benar-benar disediakan; aturan penolakan tanpa shift tetap berlaku bila profil mewajibkannya. Uji ulang dari Android berhasil sampai pembayaran, penutupan order, dan pelepasan meja.
13. **Isi Rak Display membutuhkan dua lokasi yang tertaut ke outlet sama.** Saat profil advanced pertama diaktifkan pada fixture QA, hanya ada lokasi display, pusat, dan transit; tombol “Isi Rak Display” tidak dapat melanjutkan dan memberi peringatan tentang pasangan gudang toko/display. Fixture QA kini membuat `QA-STORAGE` bertipe `store` serta menautkan gudang dan display ke outlet yang sama. Setelah itu alur Android lulus sampai saldo berpindah. Pemeriksaan kesiapan POS tetap menampilkan “POS siap digunakan” sebelum pasangan lokasi itu tersedia; ini adalah celah panduan/setup advanced yang perlu diperbaiki sebelum menyebut onboarding advanced selesai.
14. **Pengajuan opname belum terbukti selesai.** Dokumen `OPN-20261031-0001` masih berstatus Draft pada tangkapan layar terakhir setelah percobaan Ajukan pertama. Percobaan berikutnya menampilkan indikator proses, lalu emulator, server QA, dan Mongo sementara berhenti sehingga penyebab akhir tidak dapat dipastikan. Resolver `SubmitInventoryOpname` memang memerlukan konfigurasi approval; helper fixture QA sekarang menambahkan workflow auto-approval untuk modul ini, tetapi perubahan tersebut **belum diuji ulang di Android** karena database sementara sudah tidak tersedia. Ini bukan bukti adanya bug produksi maupun bukti bahwa perbaikannya berhasil.
15. **Retest opname pada fixture baru berhasil, tetapi hanya untuk retail + simple.** Dokumen dengan nomor sama pada database sementara baru benar-benar mencapai status `Selesai` dan saldo tetap 50. Skenario advanced yang terputus pada butir 14 tetap belum terbukti selesai; kedua hasil tidak boleh disamakan.
16. **Detail stok terbuang salah menyebut sumber tidak tercatat.** Data dokumen menyimpan `stock_balance_id` dan `lokasi_cabang_id`, tetapi nama lokasi pada snapshot saldo QA kosong. Perbaikan awal menghilangkan label palsu, namun masih menampilkan “Lokasi stok” karena daftar warehouse ternyata hanya dimuat untuk halaman opname. Halaman stok terbuang kini turut memuat daftar warehouse dan mencocokkan ID sumbernya. **Retest APK staging pada emulator lulus:** detail `SCR/2026/10/0001` menampilkan “Lokasi Toko QA”, bukan label generik; dokumen tetap `Selesai` dan saldo sebelumnya telah diverifikasi 49 unit.
17. **Retest valuasi PO advanced: konsisten dengan AVCO global, bukan harga lot per lokasi.** Pada fixture QA, 49 unit lama tidak memiliki biaya perolehan dan 1 unit baru diterima Rp5.000. `applyInventoryGlobalReceiving` memperbarui biaya rata-rata tertimbang (AVCO) global menjadi Rp100 per unit: filter Gudang Pusat QA (1 unit) menampilkan `Nilai Stok Rp100`, sedangkan seluruh lokasi (50 unit) menampilkan Rp5.000. `location-stock-page.service.js` memang memakai `qty × inventaris.harga_beli` global. Angka ini **bukan** bukti bug; pemahaman pengguna bisa dibantu dengan label/metode valuasi. Jurnal penerimaan untuk kasus ini kemudian direkonsiliasi pada butir 30; pada saat temuan awal dibuat jurnal tersebut belum diperiksa.
18. **Uji Android retur advanced terhenti setelah status Menunggu.** Setelah `RPO-2026100001` berhasil disimpan dan dikirim, emulator tidak merespons tap maupun tombol Home, meski ADB shell masih menjawab; tidak ada error Flutter yang tampak pada cuplikan log. Ini hambatan lingkungan uji yang perlu diulang di sesi perangkat baru, bukan bukti fitur persetujuan/proses retur lulus atau gagal.
19. **Panduan advanced sempat memberi status siap terlalu dini.** `GetPOSRuntimeConfig` sekarang menolak kesiapan konfigurasi jika `use_display_stock` aktif tetapi tidak ada pasangan gudang toko (`store`) dan lokasi display aktif dengan `linked_toko_id` yang sama serta izin arah transfer yang sesuai. Panduan Android mengarahkan masalah tersebut ke **Warehouse & Lokasi**. Tes server membuktikan kondisi tanpa display dan display pada outlet berbeda ditolak; pasangan yang benar tidak lagi memunculkan isu. `node --test tests/pos_lock.security.test.js` lulus 9/9, `flutter analyze` pada panduan lulus tanpa isu. **Belum diuji pada APK baru** karena perubahan belum dibangun/terpasang di emulator.
20. **Emulator QA mengalami ANR sistem.** Setelah percobaan retur, perangkat akhirnya menampilkan `System UI isn't responding`; reboot memulihkan layar utama, tetapi tap pada halaman PIN aplikasi staging tidak bereaksi pada pemeriksaan berikutnya. Logcat menunjukkan aplikasi mulai dan memuat halaman PIN tanpa exception Flutter yang jelas. Ini tidak dapat dipakai menyimpulkan bug aplikasi maupun kelulusan Android; jalur retur dan profil lain tetap harus diulang pada perangkat/emulator sehat.
21. **Kasir web salah mengartikan sesi kedaluwarsa sebagai toko tidak ada.** Browser admin `localhost:5173/pos/kasir` menunjukkan banyak respons 401 dan token refresh gagal, tetapi modal awal mengatakan “Toko POS belum tersedia”. `front_end_template/src/pages/pos/kasir.vue` kini membedakan kegagalan autentikasi (alih ke login), kegagalan muat toko (modal coba lagi), dan respons toko benar-benar kosong. Tes khusus `pos-kasir-onboarding-modal.test.mjs` lulus 8/8; sesudah reload browser lokal mengarah ke `/login`. Pengujian kasir web berautentikasi belum bisa dilanjutkan dari sesi browser tersebut sebelum login ulang.
22. **Reservasi meja memiliki celah pemesanan serentak.** Pembuatan dan penjadwalan ulang sebelumnya memeriksa bentrok sebelum menyimpan, sehingga dua permintaan yang tiba hampir bersamaan dapat sama-sama melihat slot kosong. Keduanya kini mengubah versi meja dan memeriksa ulang bentrok dalam satu transaksi MongoDB; transaksi yang kalah akan mencoba ulang dan melihat slot telah terisi. Uji pada replika Mongo sementara membuat dua permintaan serentak untuk meja/slot sama: tepat satu berhasil pada pembuatan dan tepat satu berhasil pada penjadwalan ulang. Seluruh tes matriks server kini **23/23 lulus**. Ini belum membuktikan UI reservasi Android/web atau resource layanan selain meja.
23. **Retest Android masih tertahan di layar PIN pada emulator QA.** Pada 31 Oktober emulator `emulator-5554` menampilkan halaman PIN staging dan jam status berjalan, tetapi dua percobaan ketuk keypad melalui ADB tidak mengubah indikator PIN. `mCurrentFocus` tetap `id.pantoo.pos.stg/MainActivity`; 350 baris logcat terakhir tidak memperlihatkan exception Flutter atau ANR aplikasi yang menjelaskan penyebabnya. Karena itu pengujian tombol retur/opname/operasi profil lain belum dilanjutkan. Perlu uji pada perangkat Android sehat atau emulator baru sebelum keputusan rilis.
24. **Kesiapan mutasi transit sebelumnya tidak memeriksa lokasi default.** Profil centralized/advanced dapat terlihat siap walau `default_transfer_transit_location_id` kosong atau tidak menunjuk warehouse transit aktif; operasi kirim lalu ditolak. `GetPOSRuntimeConfig` kini menandainya sebagai masalah konfigurasi. Uji server membuktikan issue muncul saat belum diatur dan hilang setelah lokasi transit aktif dipilih (tes `pos_lock.security.test.js` tetap 9/9 lulus). Di Android, panduan menyebut jalur **Web Admin → Inventory → Pengaturan → Operasional Gudang** karena pemilihan default transit belum ada pada aplikasi mobile; ini merupakan keterbatasan onboarding mobile yang perlu diputuskan sebelum rilis mandiri tanpa admin web.
25. **Verifikasi admin web lokal.** Setelah login ulang dan membuka PIN kasir, katalog `/pos/kasir` memuat 16 produk dummy beserta harga dan stok. Halaman `/inventory/pengaturan-inventaris` dapat dibuka; tab “Operasional Gudang” memiliki pilihan “Default Lokasi Transit”. Tidak dilakukan checkout baru atau perubahan konfigurasi produksi dalam sesi browser ini.
26. **Retest retur advanced dari Android berhasil.** Emulator staging memakai endpoint QA `10.0.2.2:8083/graphql` dan akun operator QA dengan PIN fixture 6 digit. Perangkat ternyata menerima input; tangkapan layar segera setelah ketukan pertama sempat belum menunjukkan perubahan, yang sebelumnya salah dibaca sebagai macet. Dokumen `RPO-2026100001` dibuka, disetujui, dan diproses melalui tombol Android. Status akhir `processed`; saldo Gudang Pusat QA untuk barang retur menjadi 0, jurnal `posted` seimbang Rp5.000/Rp5.000 dan `reference_id` cocok. Ini menutup retest tombol retur yang tertahan pada butir 18 dan 23, tetapi tidak membuktikan seluruh operasi profil lain.
27. **Retest opname advanced dua arah berhasil.** Dokumen `OPN-20261031-0002` dibuat di Lokasi Toko QA dengan snapshot 49, hasil fisik 48 dan alasan selisih. Setelah Ajukan dan Proses Stok pada Android, status DB `posted`, saldo lokasi 48, serta jurnal `stock_opname` `posted` dengan debit akun 6100 Rp100 dan kredit persediaan 1100 Rp100. Dokumen berikutnya `OPN-20261031-0003` dimulai dari snapshot 48, hasil fisik 49; sesudah alur Android yang sama saldo kembali 49 dan jurnal debit persediaan 1100 Rp100/kredit akun 4500 Rp100. Kedua jurnal `is_balanced=true` dan referensinya cocok dengan opname. Ini menutup retest selisih ±1 di retail + advanced, tanpa menghapus status historis percobaan pertama pada butir 14–15.
28. **PIN delapan digit yang disampaikan pengguna tidak cocok dengan aturan POS saat ini.** Layar pembuatan PIN menerima 4–6 digit dan layar buka PIN otomatis memverifikasi pada 6 digit. Pengujian di atas memakai PIN fixture QA yang sesuai aturan, bukan PIN delapan digit tersebut. Belum dipastikan apakah delapan digit itu PIN akun lain atau permintaan untuk mengubah kebijakan; jangan menganggapnya telah diuji berhasil.
